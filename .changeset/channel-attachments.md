Channel turns can carry files. `POST /channels/turn` accepts an optional `attachments` list (at most 10): each a WhatsApp photo, video, document or audio file the gateway serves from its own signed link, with `filename`, `mimetype`, `size` (at most 50 MiB, the gateway's bound), `sha256` and `kind`. A filename never refuses a turn: one over 200 code points is cut, an empty one is named by its kind. `message` still carries the caption or a placeholder. The model sees the image or the extracted text, but never the link: it, the hidden notes and the stored message metadata name a file as `channel:<16 hex of its sha256>`, resolved server-side (the run's request, then the session's `channel_attachment_links` table until the link expires). Links are fetched only from the gateway host of `CHANNEL_SERVICE_DID` under `/media/<binding>/`, without redirects, and the bytes are used only when their SHA-256 matches; they go to models as bytes, never by URL. A file that cannot be fetched, does not fit the turn's 50 MB budget or is over 25 MB (archived to the sandbox only) becomes a note; the turn always runs. Channel files are archived as `<name>-<12 hex>.<ext>`. A resumed attempt does not download them again. With semantic routing on, a placeholder-only file message stays in the current conversation and a message with files is never answered with a clarifying question. Tools read the raw list as `ctx.session.channel.attachments` (for example as claim evidence).

`@ixo/action-protocol` 0.7.0, Hub protocol level 5 on every Hub call (options still answer as level 3). **This runtime requires Auth Hub PR 86 (protocol version 5) deployed on every network first.** An older Auth Hub answers `?version=5` with `400 invalid_request`; the runtime then refuses Hub actions in plain words ("Auth Hub must be updated …") and keeps every held action and outcome (polls answer from SQLite; callbacks are refused with 409 so Auth Hub retries them). The application card `ixo.bid.submit.v1` and the claim card `ixo.claim.submit.v1` are built by the plugin that runs the claim collection through `ctx.hubActions.request`; the generic `request_hub_action` refuses them and leaves their schemas out of its prompt. Their outcomes (`authorized` → `submitted` → `succeeded` with `ixo.bid.submission.v1` / `ixo.claim.submission.v1`, or `failed` with `ixo.submission.failed.v1`; a claim may sit at `unknown` until settled) come back as outcomes. Auth Hub text given to the model (a failure `message`, a refusal `reason`) is quoted and labelled as data; a failure's technical `detail` is never given to the model (stored outcomes and the gateway relay keep receipts exactly as Auth Hub signed them, since the gateway compares whole receipts). Chain-transaction cards (`ixo.chain.tx.v1`) are unchanged.
