Parked frontend calls. A browser tool or AG-UI action whose session has no socket that can run it is no longer refused (`… was not sent: no browser is connected to session …` is gone): it is parked, unsent, and sent to the first socket of that session that passes CONNECT, oldest first and right after its `connected` event; from then it runs under its own deadline as before. A parked call ends as never sent when the turn aborts (`… was not sent: the turn was aborted`) or when the new park deadline passes: `FRONTEND_PARK_TIMEOUT_MS` (whole ms from 1 to 2147483647, default `300000`, bounded in practice by `TURN_TIMEOUT_MS`; validated by the base env schema, whose field is the only parser), with `<Browser tool|AG-UI action> <name> was not sent: no browser joined session <id> within <n> s. Ask the user to open this chat; do not retry on your own.` Both reject with the new `FrontendCallNotSentError` (`src/realtime/frontend-call-registry.ts`; `reason` `aborted`, `park-deadline`, `no-browser` or `table-full`, the last for a full table of 256 calls, parked ones included): a definite failure, for which `isUncertainOutcome` is false before it looks at the turn's aborted signal, so a write's claim is released even on an aborted turn. After a park deadline the session's later calls fail at once (`… no browser has joined session <id> since an earlier call waited <n> s for one. …`) until a socket of the session passes CONNECT. `FrontendCallRegistry.open()` takes `parkTimeoutMs` (the undispatched call's clock; `dispatched()` restarts it with the call's `timeoutMs`), gains `isParked()`, loses `fail()`, and removes its listener from the turn's abort signal however the call ends. The SSE mirror of a browser-tool invocation is emitted when the call is sent, not when it is parked. The Portal and AG-UI plugins no longer throw when `hasClient` is false. `FrontendCallSurface.canDispatch(sessionId, kind, toolName)` says whether a call would be sent now rather than parked; wallet signing (`wallet-signing.ts`: `sign_ixo_transaction`, `request_pod_signature`) uses it instead of `hasClient`, so with only a background executor connected it is `unavailable` at once, nothing sent, instead of parking in the user-wide write lane. `FrontendCallSurface.parkedFor(sessionId)` returns the session's oldest parked call as `{ kind, toolName, since }`, and the user object sets it as `RunSummary.waitingFor` (live, never persisted) on the running or recovering run in `GET /runs/active`, `GET /sessions/:id/run` and `activeRun` on `GET /sessions` rows. `GET /debug/realtime` marks each pending call `parked` and adds `parkedCalls`, and each socket's `executor` (with the kept `tools` count for a background one).

Socket executor kinds. The CONNECT auth payload may carry `executor: 'background'` and `tools: string[]`: only that exact value makes a background executor, whose tools are the valid names (`DECLARED_TOOL_NAME_PATTERN`), de-duplicated, at most 24 (`MAX_BACKGROUND_EXECUTOR_TOOLS`), cut further only when the Hibernatable WebSocket attachment (where the kind and tools are stored; Workers caps it at 2,048 bytes) would exceed a 2,000-byte JSON budget (`SOCKET_ATTACHMENT_BUDGET_BYTES`), with one warning counting the dropped names; only the first 96 entries of `tools` are read, the rest counted as over the cap. The `connected` event carries `executor: 'foreground' | 'background'`, the kind the runtime accepted. `SessionSocketHub.executorFor(sessionId, kind, toolName)` replaces `executorForSession`: the most recently active foreground socket, else, for a browser tool, a background executor that declared it (never for an AG-UI action), else none (the call parks). Fan-out (`emitToSession`) skips background executors and encodes an event only when a foreground socket of the session takes it, and a session drains (history indexing) when its last foreground socket goes; `hasClient`, the socket counts and the `status` event count every authenticated socket.

Frontend and per-session lanes for the tool scheduler. `PluginTool.surface?: 'frontend'` (also on the `tool()` helper) marks a tool that acts in the user's browser through the frontend bridge: it runs in its session's own `frontend:<sessionId>` lane, one call at a time per session, never in the user-wide read or write lanes, so a call parked while its chat has no tab holds no slot another chat needs. The Portal's browser tools and AG-UI actions declare it, reads and writes alike; every other bundled tool is server-side and keeps its lane by effect. Sub-agent dispatches run in a lane per session too (`subagent:<sessionId>`, four at a time), so a sub-agent waiting on a parked inner call holds only its own chat's slots. User-wide, writes still run one at a time and reads four at a time. `ToolScheduler.run(lane, signal, action, sessionId?)` takes the lanes `read`, `write`, `frontend` and `subagent` (the last two need the session id, keyed by `sessionLaneKey`, created on demand and dropped once idle); `snapshot()` reports `read`, `write`, `frontend` and `subagent` (the last two summed) and `sessionLanes` (only the busy ones), and `GET /debug/runs` now includes it as `tools`. `createToolExecutionMiddleware` takes `laneOf(toolName): ToolLane` and a new `effectOf(toolName)`: a write is claimed in the ledger by its effect, whatever its lane, and a frontend write's fingerprint (`operationKey(name, args, sessionId)`) names its session, so the same browser action in two chats is two actions. `RunStore.claimWrite` never takes over a `pending` claim of another run that is still active: it answers `blocked` and leaves the row, so the owner's release still deletes it. `MainAgentBuildResult.toolSurfaces` lists the browser tools, a sub-agent's inner tools included (a name two tools disagree on stays server-side).

Parked calls across a restart, and declared browser-tool effects. `turn_tool_marks` gains a nullable `sent_at` (added to an existing table, whose marks count as sent), set by `RunStore.markSent(runId, toolCallId)` when a frontend call reaches a socket and cleared by `bumpMark`: `FrontendCallRegistry.open()` takes `onDispatched`, called once from `dispatched()` and never for a call that ends unsent, `FrontendCallParams.onDispatched` forwards it, and the Portal and AG-UI tools pass the new `RuntimeContext.markDispatched` (present when the host keeps tool marks and the call has an id). On resume, a started, unfinished mark of a frontend tool (`createToolMarksMiddleware`'s new `surfaceOf`) with no `sent_at` was parked and never sent, so it runs again whatever its effect, instead of getting the unknown-outcome result; a sent one keeps the read / write rule. `toolEffectOf` reads the camelCase forms of its read verbs (`getEntityProfileDomain`, `listRooms`) and adds `find` (`find_…`, `findEntity`). A browser tool declaration in the turn body may carry `effect: 'read' | 'write'` (any other value is ignored, the tool kept; `declaredToolEffect`), which the Portal tool takes as its effect, except the human-decision tools, which stay writes.
