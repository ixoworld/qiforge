Concept

An Agentic Oracle is a bounded agent

Not a general-purpose AI assistant. Not a chatbot with a bigger context window.

Declared identity

Who it is and how it behaves.

Explicit capabilities

It can only do what you gave it — nothing more.

Written policy

When to act, when not to, when to call a human.

The value comes from the bounds being explicit, auditable, and honest — not from the model being powerful.

The core idea

The trust boundary

The line between what the oracle decides on its own, and what a human must handle.

Inside the boundary

Routine, resolvable, low-risk. The oracle acts and records.

Outside the boundary

Refunds, legal, security, angry customers, anything ambiguous. The oracle escalates.

QiForge enforces this structurally — the oracle can only call tools that exist. It can't do what you never gave it.

Architecture

An oracle is thin

Identity, a prompt, a list of plugins. The runtime does the rest — auth, sessions, Matrix, state, routing.

The mental model

A plugin is three things

01

Tools

The actions the oracle can take. Typed input, a handler. The hands.

02

Manifest

When to act, when not to, when to escalate. Compiled into the prompt. The judgment.

03

Config schema

Env vars it needs, validated at boot. Missing = boot fails loudly. The safety.

That's the whole API. An identity + one plugin + a few tools is a complete, deployable oracle.

Design choice

Three ways to give an oracle Linear

1 · Custom tools

Write the tools yourself. Narrow, deterministic, audited.

client-facing

← what we build today

2 · Linear MCP

Linear hosts an MCP server. Connect it → the agent gets Linear tools with zero client code.

mcp.linear.app

linear.app/docs/mcp

3 · Composio

Bundled plugin. Linear + 100s of SaaS apps through one integration.

internal copilot

The choice follows the trust boundary: client-facing → custom/MCP with a tight tool set. Internal copilot → Composio's broad gateway is fine.

Build · step 1

The client — fetch + Zod, no SDK

plugins/linear/linear-client.ts 
export async function createIssue(params, signal) {
  const data = await linearGraphql(
    params.apiKey,
    `mutation CreateIssue($input: IssueCreateInput!) {
       issueCreate(input: $input) {
         success
         issue { id identifier title url priority }
       }
     }`,
    { input: { teamId, title, description, priority } },
    responseSchema,   // Zod-validate what comes back
    signal,
  );
  return toTicket(data.issueCreate.issue);
}

The agent never sees this file. It returns plain objects the tools hand back.

Build · step 2

The tools — the oracle's hands

create_ticket

Files a Linear issue. Called on every case.

comment_on_ticket

Logs progress on an existing ticket.

get_ticket

Looks a ticket up by its identifier.

escalate_to_human

Hands the case to a human via Matrix.

Each tool: a name, a description, a Zod schema, and a handler. The description is part of the prompt — write it for the model.

The "wait, that's it?" moment

Escalation is five lines

plugins/linear/linear-tools.ts · escalate_to_human 
// ctx.matrix is on EVERY tool — the runtime provides it.
// No Matrix client setup. No credentials in plugin code.
await ctx.matrix.postToRoom(escalationRoomId, {
  msgtype: "m.text",
  body: `🚨 Support escalation\nReason: ${reason}\n\n${summary}\n\nTicket: ${ticketUrl}`,
});

The escalation isn't infrastructure you build. Matrix is already in every tool's hands. You write the policy that decides when to call it.

Build · step 3

The manifest is the policy

plugins/linear/linear.plugin.ts · manifest 
whenNotToUse: [
  "Refunds, chargebacks, billing disputes — escalate, never decide these.",
  "Legal threats, account access, or security issues — escalate.",
  "A visibly angry or repeat-unhappy customer — escalate.",
  "Anything you are unsure about — escalate. Never guess.",
],

The agent reasons over this. You tune the oracle's judgment by editing English and re-running the case — not by changing code.

Build · step 4

Config schema — fail loud

plugins/linear/linear.plugin.ts · configSchema 
const configSchema = z.object({
  LINEAR_API_KEY:            z.string().min(1),
  LINEAR_TEAM_ID:            z.string().min(1),
  SUPPORT_ESCALATION_ROOM_ID: z.string().min(1),
});

Miss one and the oracle refuses to boot with an error naming the linear plugin. No silent half-working state.

✗ Forgot the room id? You find out at boot — not when a customer's escalation vanishes.

Attach it

Wire it into the agent

plugins/linear/linear.plugin.ts 
export class LinearPlugin extends OraclePlugin {
  name = "linear";
  manifest = manifest;
  configSchema = configSchema;

  // Only loads when LINEAR_API_KEY is set — so the reference
  // oracle still boots cleanly without Linear creds.
  autoDetect(env) { return Boolean(env.LINEAR_API_KEY); }

  getTools(ctx) { return [createTicket, comment, getTicket, escalate]; }
}

Then add new LinearPlugin() to the plugins array in main.ts. Done.

Write the agent

Give it an identity

apps/qiforge-example/src/config.ts 
export const config = {
  name: "Acme Support Oracle",
  org: "Acme",
  description: "Front-line customer support for Acme.",
  prompt: {
    opening: "You are Acme's support oracle. File a ticket for every"
      + " case. Resolve what you can; escalate anything risky or"
      + " ambiguous. Be warm, concise, and never guess.",
  },
};

Identity sets the voice. The manifest sets the routing. Together they're the whole brain.
