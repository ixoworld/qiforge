The problem

Building an AI agent properly is a mountain of plumbing

Before your agent says a single useful word, you need:

Auth & identity

Memory that survives restarts

Per-user state

Safety / loop-breaking

Tool wiring & validation

Web · Matrix · Slack channels

Most teams spend weeks here and never get to the actual agent.

The answer

QiForge is a framework for building agents

You write ~30 lines. It hands you a production-grade AI agent — an Oracle.

You bring

An identity, a prompt, and your custom capabilities.

QiForge brings

Everything else — the whole plumbing mountain, already wired.

An Oracle = a bounded AI agent with a declared identity, explicit capabilities, and a written policy. It can only do what you gave it.

What you get for free

The runtime hands you…

  • A wired NestJS app — HTTP + WebSocket, validation, rate limiting, Swagger
  • UCAN auth on every request
  • An on-chain identity for the oracle
  • Encrypted per-user storage, synced via Matrix
  • A LangGraph agent rebuilt per request
  • Always-on safety middlewares
  • 15 bundled plugins behind simple toggles
  • A typed plugin API for everything custom

You focus on what makes your agent special. The framework does the rest.

Part 2 · What is a plugin?

A plugin is three things

01

Tools

The actions the agent can take. Typed input, a handler. The hands.

02

Manifest

When to act, when not to, when to escalate. Becomes part of the prompt. The judgment.

03

Config schema

Env vars it needs, validated at boot. Missing = boot fails loudly. The safety.

That's the entire API surface. Learn these three and you can build anything.

Part 2 · What is a plugin?

The manifest is the judgment

The agent reasons over plain-English rules. No routing if statements anywhere.

// the plugin tells the agent WHEN to reach for it
whenToUse:    [ "A customer reports a problem — file a ticket first." ]
whenNotToUse: [ "Refunds or billing disputes — escalate, never decide." ]

You tune the agent's behaviour by editing English — then re-running the case. The tools stay dumb and auditable.

Part 3 · Build · step 1 of 4 — the client

Talk to Linear: fetch + Zod

plugins/linear/linear-client.ts 
export async function createIssue(params, signal) {
  const data = await linearGraphql(params.apiKey,
    `mutation { issueCreate(input: $input) {
        success  issue { id identifier title url } } }`,
    { input: { teamId, title, description, priority } },
    responseSchema,  // validate what comes back
    signal);
  return toTicket(data.issueCreate.issue);
}

No SDK. The agent never sees this file — it returns plain objects the tools hand back.

Part 3 · Build · step 2 of 4 — the tools

Wrap it as a tool

plugins/linear/linear-tools.ts 
tool(async (args, ctx) => {
  const { title, description, priority } = schema.parse(args);
  const ticket = await createIssue({ ...config, title, description, priority });
  return JSON.stringify(ticket);
}, {
  name: "create_ticket",
  description: "File a support ticket. Call for EVERY case.",
  schema,   // Zod — the model only sees valid args
});

A name, a description (the model reads it), a Zod schema, a handler. Done.

Part 3 · The "wait, that's it?" moment

Escalation is five lines

plugins/linear/linear-tools.ts · escalate_to_human 
// ctx.matrix is on EVERY tool — the runtime provides it.
// No Matrix client setup. No credentials in plugin code.
await ctx.matrix.postToRoom(escalationRoomId, {
  msgtype: "m.text",
  body: `🚨 Escalation: ${reason}\n${summary}\nTicket: ${ticketUrl}`,
});

The escalation isn't infrastructure you build. Matrix is already in every tool's hands — you just write the policy that decides when to call it.

Part 3 · Build · step 3 of 4 — the policy

Write the manifest

plugins/linear/linear.plugin.ts · manifest 
whenNotToUse: [
  "Refunds, chargebacks, billing disputes — escalate, never decide.",
  "Legal threats, account access, or security issues — escalate.",
  "A visibly angry or repeat-unhappy customer — escalate.",
  "Anything you are unsure about — escalate. Never guess.",
],

This is where the support agent's judgment lives. Change the behaviour → edit this list.

Part 3 · Build · step 4 of 4 — config

Declare your env — fail loud

plugins/linear/linear.plugin.ts · configSchema 
const configSchema = z.object({
  LINEAR_API_KEY:             z.string().min(1),
  LINEAR_TEAM_ID:             z.string().min(1),
  SUPPORT_ESCALATION_ROOM_ID: z.string().min(1),
});

Miss one and the oracle refuses to boot, naming the linear plugin and the missing var. ✗ No silent half-working state.

Part 3 · Build · the whole thing

Snap it together

plugins/linear/linear.plugin.ts 
export class LinearPlugin extends OraclePlugin {
  name = "linear";
  manifest = manifest;          // the judgment
  configSchema = configSchema;  // the safety

  autoDetect(env) { return Boolean(env.LINEAR_API_KEY); }  // load only if configured
  getTools()      { return [ createTicket, comment, getTicket, escalate ]; }  // the hands
}

Three things — tools, manifest, config — in one class. This is the plugin.

Part 4 · Give it a personality

Identity + features in config

src/config.ts 
export const config = {
  name: "Acme Support Oracle",
  org:  "Acme",
  prompt: { opening: "You run front-line support. File a ticket for"
    + " every case; resolve what you can; escalate anything risky." },
  features: {            // flip bundled plugins on/off
    memory: true, "user-preferences": true, composio: true,
  },
};

Identity sets the voice. The manifest sets the routing. features picks the bundled powers.
