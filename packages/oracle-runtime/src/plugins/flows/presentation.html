The idea

You describe it. The agent builds the real thing.

User “When a claim is submitted, email the applicant a confirmation and notify the team.”

→ The agent adds the steps, wires outputs into inputs, sets conditions / schedules / assignees, pre-fills forms, and explains what it built. Built on @ixo/editor’s Qi Flow engine — the same flows the portal already runs.

Why it’s safe

A builder, not a runner

Agent
writes flow docs · pre-fills forms
→
Flow room
the shared document
←
User · Portal
reviews · signs · RUNS
  • The agent authors and reads flow documents. That is its entire capability.
  • No execution, no signing, no UCAN minting, no keys — all running stays in the portal, driven by the user.
  • Worst case of a bug = a malformed doc in a room the user owns — visible and discardable before they run it.

Edit in place — no new room

User “Read the current flow, then add a step that emails me after the last one, and change the first step’s title to ‘Intake’.”
read_flow→ add_step→ update_step
  • Per-block edits — changing one step never disturbs the others’ inputs, conditions, or run state.
  • “Why did step 2 fail?” → flow_status reads the live run state and reports the exact error.
  • No flow open? “What actions can I use? Give me a template.” → works instantly, no room needed.

The key design

One friendly model — internals never leak

The agent works only on FlowSpec: steps, actions, inputs, conditions, schedules, forms. It never sees a block, Y.Doc, can/with, CAR, CID, or delegation.

Agent
FlowSpec only
→
Translator
FlowSpec ⇄ BaseUcanFlow
→
Read · Edit · Compile
against the Yjs doc
  • One translator module owns the projection, with exhaustive round-trip tests.
  • A leak-guard test asserts no tool’s schema or output exposes an editor primitive.
The surface

27 tools, loaded on demand

Discover
  • list_actions — browse the available actions
  • describe_action — full spec of one action
  • list_referenceable_fields — what a step can pull from upstream
  • get_flow_template — start from a ready-made flow
Inspect
  • read_flow — see the whole flow, cleanly
  • get_step — read one step + its status
  • flow_status — what ran, failed, or is blocked
  • explain_step — plain-language: what a step does
Author
  • validate_flow — check it before saving
  • create_flow — start a brand-new flow
  • add_step — add a step, others untouched
  • remove_step — remove a step (guards references)
  • reorder_step — move a step's position
  • update_flow_meta — rename / set the goal
  • connect_steps — wire one output into an input
  • update_step — change several settings at once
Tune a step
  • set_step_inputs — set the step's inputs
  • set_step_conditions — gate it on a value
  • set_step_schedule — set a due date / window
  • set_step_assignment — who's meant to run it
  • set_step_confirmation — force a confirm before running
  • set_step_trigger — manual or at flow start
Forms
  • describe_form — the form's questions + allowed values
  • fill_form — pre-fill answers (never submits)
Linkage
  • check_link — can this output feed that input?
  • compatible_actions — what can produce this value
  • requirements — an action's prerequisites
Under the hood

Hard problems we solved

Conditions that actually fire

The compiler writes operators the FE evaluator can’t read. We author conditions directly in the evaluator’s vocabulary — so a condition the agent sets really gates the step.

Per-block isolation

Edits are deltas. Changing one step never rewrites or drops another step’s inputs, conditions, or run state. Proven by test.

Lossless read

Per-block props live only in the document fragment; the graph map drops them. The read gathers from all three sources for the true flow.

Room access

The front-end creates the room, grants the oracle power 50, and invites it — the oracle can author while the user stays the owner.
