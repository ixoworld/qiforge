## 1.99.7

### Patch Changes

- [#529](https://github.com/ixoworld/qiforge/pull/529) [`7a246d9`](https://github.com/ixoworld/qiforge/commit/7a246d95830a1d5bb5dee9150e0e059b0a2382d1) Thanks [@Michael-Ixo](https://github.com/Michael-Ixo)! - Every LangChain package moves to its current release: `@langchain/core` 1.3.4, `langchain` 1.6.1, `@langchain/langgraph` 1.6.1, `@langchain/langgraph-checkpoint` 1.2.2, `@langchain/openai` 1.8.0 (`openai` 7.50), `@langchain/mcp-adapters` 2.0.2 (`@modelcontextprotocol/client` 2.4), `langsmith` 0.11.8, and in `@ixo/common` `@langchain/anthropic` 1.6.0, `@langchain/langgraph-checkpoint-sqlite` 1.1.0, `@langchain/textsplitters` 1.0.2.

  Workers runtime:

  - Platform models and the API-key BYO lanes use `ChatOpenAICompletions`. `ChatOpenAI` 1.5.14+ sends every `gpt-5.6` model id to the Responses API, which would have moved OpenRouter calls to `/responses`. The request body is the same as before the upgrade.
  - MCP plugins use `MCPAdapter` in legacy mode, with no SSE fallback. Tool names are unchanged. A result reaches the model once; a result that is only structured content now arrives as its JSON. Images, audio and files in a tool result arrive as one line of text naming them, because a tool message carries text only. The pnpm patch for the JSON-schema validator is gone: the MCP client picks a validator without code generation on Workers.
  - The checkpoint saver stores each pending write's task path and returns writes in task-path order (migration 004 adds one column and rewrites no rows).
  - A conversation summary gets an id of its own. Upstream now gives it the id of the first message it condenses, which would have replaced that message's row in the transcript.
  - `create_artifact` returns a failed result when the store fails twice, so the reply still ends there. A return-direct tool that throws now gives the model another call.
  - The context guard reads the loaded plugins from the graph state, so it keeps a load result while its plugin is loaded, as documented.
  - Tool cards (`tool_call` and `action_call` frames) carry the call's real arguments. Core used to hand the stream one JSON string under `input`.
  - Tracing: the runtime removes LangChain's tracing switches from `process.env` at start, so only its own redacting tracer ever runs; a restricted turn is never traced. Errors and metadata are redacted too, and model headers are no longer uploaded.
  - The BYO OpenAI lane sets its base URL, so no environment variable can redirect a user's key.
  - File attachments reach the model under their own name, not `LC_AUTOGENERATED`.
  - A read tool is not run again after an error marked as not retryable; a gateway error on an MCP write is treated as an unknown outcome; the asks plugin detects an expired token from the error's status.
  - Tool validation no longer writes the whole message list back before every model call.
  - The main agent runs each tool call of a step as its own graph task again (`createAgent` `version: 'v2'`): a call's result is checkpointed when it returns, so a durable run resumed after a reset in the middle of a step no longer re-runs the reads that had finished or reports the writes that had finished as "outcome unknown". langchain 1.5.19+ no longer copies the whole state into each task, which was why the main agent had one task for all calls.
  - A call to an Anthropic model on OpenRouter (`anthropic/…`) sends a top-level `cache_control: { type: 'ephemeral' }`, so Anthropic caches the prompt prefix for 5 minutes. Requests to every other model are unchanged; the BYO Anthropic lane sends nothing new.
  - Every call to a GPT-5.6 model on OpenRouter (`openai/gpt-5.6-luna`, `-terra`, `-sol`), on any role, asks for OpenAI, then Azure (`provider.order`, fallbacks allowed). For `gpt-5.6-luna`, the reply model used to go to the lowest-latency provider (Amazon Bedrock) and the helper roles to OpenRouter's default routing, and Bedrock often lost the prompt cache between repeated calls. Other models are routed as before: `provider.sort: 'latency'` on the reply model, OpenRouter's default routing on helper roles.
  - OpenRouter requests no longer carry a top-level `require_parameters: true`. It is not an OpenRouter request field and had no effect.
  - BYO models (ChatGPT subscription, OpenAI key): the picker offers the models the user's account has. On connect (and on `GET /byo-llm/status?refresh=true`, or when none is kept) the runtime reads the provider's own listing (`GET /v1/models`; the ChatGPT backend's `GET /models?client_version=`), keeps it per user in the object's storage and narrows the curated list to it. `status` reports `modelSource` (`account` or `catalog`) and, when the list could not be read or the provider has none, `modelSourceNote`.
  - A BYO model call is taken as a refused model only when the provider says so (`model_not_found`, `unsupported_model`, "does not exist", "is not supported" …). A bare HTTP 400 or 404, an empty body, or a 400 about another field (for example `call_id` longer than 64 characters) is an ordinary failed turn, no longer a silent switch to the platform model with a "doesn't offer this model" notice. LangChain's own "Troubleshooting URL … MODEL_NOT_FOUND" suffix on every 404 is ignored. The notice carries the provider's `status` and `code`.
  - The ChatGPT lane no longer fails a replayed thread whose stored tool call id is longer than the backend's 64 characters (for example a sub-agent's forwarded call, renamed `<parent id>_<id>`, or another provider's id). The outgoing request carries `call_` + the base64url SHA-256 of the id (48 characters, the same every time, one per distinct id, a call and its output alike); the stored message, tool marks and transcript keep the original. A request in which that would equal another call id is refused.

  `@ixo/common` moves to `openai` 7, so the workspace resolves one copy of each LangChain package.

  Tested on a devnet oracle: platform models (GPT-5.6, Anthropic), MCP tools, the sandbox and the BYO ChatGPT lane. The BYO OpenAI-key lane was not tested live (unit tests only).

## 1.99.5

### Patch Changes

- [#498](https://github.com/ixoworld/qiforge/pull/498) [`1e0203e`](https://github.com/ixoworld/qiforge/commit/1e0203eb8fda7f17bf266a0e99c1f3a39326a783) Thanks [@Michael-Ixo](https://github.com/Michael-Ixo)! - Pick up `@ixo/ucan` 2.4.0, which refuses re-labelled UCANs. A UCAN archive's block CIDs are written by its sender and no signature covers them, so one signed invocation or delegation could be re-sent under another CID (a sha2-512 CID over the same bytes, its JWT form, a CBOR block with an empty nonce) and slip past a replay store or revocation check keyed on that CID. `validate()` and `validateDelegation()` now refuse with `INVALID_FORMAT` any archive whose UCANs do not sit under the CID derived from their signed form, and refuse JWT-form UCANs. The runtime's HTTP shell, the deposited-delegation check and the IXO Channels ingress all validate through the library, so they refuse such tokens too. These packages pinned `@ixo/ucan` 2.3.0 (directly, or through `@ixo/oracles-chain-client`); they now pin 2.4.0.

## 1.99.0

### Minor Changes

- [#329](https://github.com/ixoworld/qiforge/pull/329) [`8efad56`](https://github.com/ixoworld/qiforge/commit/8efad567fc8dfdcf996d3b16cecadf9aa231bae5) Thanks [@ig-shaun](https://github.com/ig-shaun)! - Split agent-facing tools into an `orchestration` plane (the default) and an `admin` plane (`tool(handler, { …, plane: 'admin' })`).

  Workers runtime: an admin tool requires `admin-tool/invoke` on `ixo:qiforge:admin-tool/<pluginName>/<toolName>` (`adminToolCapability`), checked by the same matcher as `manifest.requires`: a grant on `ixo:qiforge:admin-tool/<pluginName>` covers that plugin's admin tools, `ixo:qiforge:admin-tool` all of them, `*` everything, and an expired delegation grants nothing. Admin tools the turn's delegation does not grant are hidden entirely — never bound (main agent and sub-agents, including `forwardTools`), never in the Tier-1 prompt or a manifest example, never in `load_capability`'s tool list; a plugin left with no usable tool is not listed by `list_capabilities` (not even as unavailable), is refused by `load_capability` like an unknown name, and is not offered to the capability router. The capability gate refuses a call naming a withheld tool, and `wrapPluginTool` re-checks the capability right before the handler. The delegation checked is the one the user issued to the oracle (on a Matrix turn, the stored one), so an admin grant records the user's consent for their own turns, not operator authority: a user can issue it to themselves.

  Node runtime (deprecated): admin tools require `invoke` on `ixo:qiforge:admin-tool:<toolName>`.
