# @ixo/ucan

## 2.3.0

### Minor Changes

- Chain-walk hardening that services kept re-implementing on top of the validator, now in the validator. Every item is backward compatible: the defaults only refuse tokens no real client produces, and the new rules are opt-in.

  - **Proof-chain shape limits.** `validate()` and `validateDelegation()` bound the RAW proof tree of a token before any signature is verified or DID resolved: at most 10 links deep, 64 nodes visited, 16 proofs and 32 capabilities on one link, 16 distinct issuers, and 256 units of verification work (each node costs its capability count times one plus the work of its proofs, so every path is charged at every link it passes through; a unit is about one signature check, so a token at the limit costs about a quarter of a second). A 3-link chain scores 4, a 10-capability grant re-delegated once 111 — `DEFAULT_PROOF_CHAIN_LIMITS`. ucanto verifies every proof it reaches, backtracks through every path with no de-duplication and branches on every capability of a proof that could match, so a 5 KB token that references the same proof blocks three-wide at every level, or repeats a capability three times at each of ten links, cost seconds of CPU and produced a multi-megabyte error. A token over a bound fails with `INVALID_FORMAT`. Override single bounds with `proofChainLimits: { maxProofsPerLink: 64 }` (an `undefined` key keeps its default), or disable the check with `proofChainLimits: false`. Invalid values throw a `RangeError` when the validator is created. New exports: `ProofChainLimits`, `DEFAULT_PROOF_CHAIN_LIMITS`.
  - **Bounded error messages.** `error.message` is at most `maxErrorMessageChars` long (default 1,024, `DEFAULT_MAX_ERROR_MESSAGE_CHARS`); a longer message is cut and ends with `…`. ucanto's messages can enumerate every explored path of a proof tree. Real messages are far shorter and unchanged.
  - **Capability pinning.** `validate()` takes a fourth, optional argument `{ expect: { can?, with? } }`: the capability ucanto authorised must equal it exactly (no `/*` tolerance; `with` compared in the URL-canonical form ucanto reports, so `IXO:x/A` and `ixo:x/A` are the same resource), else `UNAUTHORIZED`. ucanto authorises the first capability it can prove, which may not be the one a service read from the invocation and routes by. `nb` is not pinned: act on `result.capability`, and set `maxCapabilities: 1` when clients mint one capability per invocation. New export: `ValidateInvocationOptions`.
  - **Capability count.** `maxCapabilities` (default unlimited) refuses an invocation carrying more capabilities than that with `INVALID_FORMAT`, before any verification. A service that mints one capability per invocation sets 1.
  - **Universal resource.** `allowUniversalResource: false` refuses a capability on ucanto's universal resource `ucan:*` anywhere in a token or its proof chain with `UNAUTHORIZED`. Default `true` (unchanged behaviour).
  - **DID resolution memoised per validation.** Within one `validate()` or `validateDelegation()` call each DID is resolved once, however many links it issues (an owner who attached every grant it holds, an agent that re-shared twice); a lookup that failed is not retried within that call either. Nothing is cached across calls; the resolvers' own `cacheTtlMs` remains the cross-request cache.
  - **Resource-scoped self-issue names the authority only.** An issuer outside `rootIssuers` may self-issue on a resource whose AUTHORITY is its DID: the whole resource, the part after the scheme (`ixo:did:key:z6Mk…`, `ixo:tenant:did:key:z6Mk…`, optionally followed by `/path`), or the first path segment under a named authority that is not itself a DID (`ixo:tenant/did:key:z6Mk…/files`). A DID authority must equal the issuer: `ixo:did:web:alice.com:did:key:zBob` names a DID Alice controls, not Bob. Before, a DID matched as a whole segment at ANY depth, so a resource that merely mentioned the issuer deeper in its path (`ixo:filesystem/alice/did:key:z6Mk…`, Alice's folder shared with that DID) let the issuer self-issue on it and be reported as its root. The new rule is strictly tighter than the old one. Visible to callers: a DID below the first path segment, or below or suffixed to a DID authority, no longer self-issues. `resourceNamesIssuer` is exported.
  - **Incomplete chains.** A proof that travelled as a bare CID link (its block not embedded in the token) fails with `UNAUTHORIZED` in both methods. Before, `validate()` under `rootIssuers: ['*']` and `validateDelegation()` threw on it and reported `INVALID_FORMAT`.
  - `VERSION` now reports the package version (`2.3.0`; it said `2.2.0` since 2.2.0).

## 2.2.1

### Patch Changes

- [#339](https://github.com/ixoworld/qiforge/pull/339) [`77012a8`](https://github.com/ixoworld/qiforge/commit/77012a8ef4ba6f2c5b7403635a1e6d232510cc69) Thanks [@Michael-Ixo](https://github.com/Michael-Ixo)! - Validator, replay store and resolver hardening.

  - **Authorised capability.** `validate()` checks the resource against, and reports as `capability`, the capability ucanto actually authorised. Before, it used the invocation's first capability, so an invocation listing an unproven capability first and a proven one second was accepted for the unproven resource and reported the unproven `can`/`with`/`nb`. Visible to callers: `capability.nb` is now the value read through the capability definition's `nb` schema, so caveat fields the schema does not declare are no longer returned, schema defaults are applied, and `nb` is `undefined` when no caveat is set. A multi-capability invocation is accepted only for the resource of the first capability ucanto can prove for the requested ability; a later capability on another resource no longer counts.
  - **Resource-scoped self-issue.** An issuer outside `rootIssuers` may self-issue only on a resource that names its DID exactly or as a whole segment (the DID starts the URI or follows `:` or `/`, and ends it or is followed by `/`). Before, any substring matched, so `did:web:victim.co` could self-issue on `…/did:web:victim.com`. Visible to callers: a resource where the DID is followed by anything other than `/` (for example `?`, `#` or `:`) no longer self-issues.
  - **Replay protection.** The invocation's CID is reserved before verification and released when validation fails, so two concurrent presentations of one invocation can no longer both succeed, and a rejected attempt does not use up the token. The mark now lives until the invocation's own expiry plus one minute (the store's default TTL only for an invocation without expiry). `InvocationStore` gains optional `addIfAbsent(cid, ttlMs)` and `delete(cid)`; a store with `addIfAbsent()` is race-free across instances. Visible to callers: with a custom store that has only `has()`/`add()`, a second presentation of an invocation that arrives while the first is still being validated through the same store object is refused with `REPLAY`, even if the store's `has()` always answers `false`.
  - **In-memory store.** `InMemoryInvocationStore` implements `addIfAbsent()` and `delete()` and takes `maxEntries` (default 100,000): at the cap it sweeps expired entries (at most once per second), then evicts the oldest. New exports: `InMemoryInvocationStoreOptions`, `DEFAULT_INVOCATION_STORE_MAX_ENTRIES`.
  - **Expiry and not-before.** `validate()` reports the earliest expiry over every delegation in the verified authorization, not over the raw first proof. `validateDelegation()` takes the earliest expiry and the latest not-before over every proof, not just the first: a chain with any expired proof fails with `EXPIRED`, and one whose not-before is in the future fails with `UNAUTHORIZED`.
  - **did:ixo resolver.** `createIxoDIDResolver` aborts a resolution after `timeoutMs` (default 3,000 ms, also when a custom `fetch` ignores the signal) and can cache successful resolutions with `cacheTtlMs` (default 0, off) and `cacheMaxEntries` (default 1,000); with the cache on, concurrent lookups of one DID share one request, and failures are never cached. New exports: `DEFAULT_IXO_RESOLVER_TIMEOUT_MS`, `DEFAULT_IXO_RESOLVER_CACHE_MAX_ENTRIES`. Invalid option values throw a `RangeError` when the resolver is created. Visible to callers: an indexer that takes longer than 3 s now fails resolution instead of waiting.
  - **Non-Ed25519 keys.** The did:ixo and did:web resolvers turn only Ed25519 multicodec keys (`0xed01` + 32 bytes) into `did:key`s and skip every other verification method; the validator also drops keys a custom resolver returns that are not Ed25519 `did:key`s. Before, such a key listed ahead of the real one failed the whole validation with `INVALID_FORMAT`.
  - **did:web over HTTP.** Only the hosts `localhost`, `127.0.0.1` and `[::1]` (with an optional port) are fetched over `http://`. Before, any domain starting with `localhost` (`localhost.example.com`) was. Visible to callers: `127.0.0.1` and `[::1]` now use HTTP where they used HTTPS.
  - **did:web resolver.** `createWebDIDResolver` takes the same `timeoutMs` (default 3,000 ms), `cacheTtlMs` (default 0, off) and `cacheMaxEntries` (default 1,000) options as the did:ixo resolver, with the same rules: the timeout covers every request of one resolution (including the HTTP fallback), only successful resolutions are cached, and concurrent lookups of one DID share one request while the cache is on. Visible to callers: a did:web host that takes longer than 3 s now fails resolution instead of waiting.
  - **Global fetch.** Both network resolvers read `globalThis.fetch` when they look a DID up, not when they are created, so a resolver built at module load uses the fetch the environment provides at run time. A `fetch` passed in the config is used as before.
